# osm-d v0.4.0

v0.4.0 turns the post-v0.3 editor-facing work into a supported release line.
It remains a standalone OSM data library: protocol, synchronization and
replication semantics now live in osm-d, while generic transport,
compression, credentials, scheduling, persistence and UI policy remain in
their respective layers.

## Highlights

### OSM topology, complete objects and areas

New supported facades:

```d
import osm.topology;
import osm.complete;
import osm.area;
```

Consumers can resolve OSM references, walk bounded/cycle-safe topology,
project complete Way/Relation children, calculate exact OSM-native location
bounds and structurally assemble closed-Way/multipolygon rings with provenance.

Generic geometry, projection, clipping, spatial indexing and rendering remain
outside osm-d.

### Changesets and Editing API protocol

New supported facades:

```d
import osm.changeset;
import osm.api;
```

`EditingApiClient` provides OSM Editing API 0.6 operations over an injected
`transport-d` `HttpExchange`: capabilities/permissions, current/specific/
history/full reads, Changeset create/read/update/close and osmChange diff
upload.

Authorization remains request-scoped. osm-d does not persist credentials,
perform OAuth/account selection, choose a write server implicitly or own
retry/background policy.

### Authoritative history, refresh and conflicts

```d
import osm.history;
import osm.sync;
```

Historical values preserve deletion semantics without inventing missing data.
Structured base/local/remote conflict facts and authoritative reconciliation
reuse the editable store's stable handles and maintained parent indexes.

The library reports facts and conflict boundaries; the application decides how
to present or resolve them.

### Replication and incremental synchronization

```d
import osm.replication;
```

The complete supported path is now:

```text
caller-selected ByteSource
  -> compression-d streaming GZIP
  -> osmChange
  -> sequence/object-version replay semantics
  -> transactional OsmStore reconciliation
  -> caller-persisted checkpoint
```

`applyGzipReplicationStep` distinguishes transport, compression, XML and
semantic/apply failures before checkpoint advancement.

M19 connected qualification covers restart/replay, explicit gaps, overlapping
timestamps, create/modify/delete, parent-index coherence, truncated input and
local dirty conflicts.

The retained LDC release workload processed 1,000 compressed sequences at
1,051.21 sequences/s on the qualification runner, with 10,016 KiB process peak
RSS. Those values are CI evidence, not universal throughput guarantees.

The qualification also found and fixed a release-only correctness defect:
authoritative Store mutations had been evaluated inside `assert(...)`, which
allowed release builds to remove the mutation expressions themselves.

## API compatibility

v0.4.0 deliberately introduces no supported v0.3.x source break.

The v0.3 facades remain supported, and the new focused v0.4 facades are added
to the patch-line compatibility contract. See:

- `docs/API_STABILITY.md` for the frozen v0.4.x contract;
- `docs/API_V0_4.md` for the v0.3 -> v0.4 migration guide.

The package root remains curated rather than re-exporting all specialized
families.

## Toolchain

The compiler floor remains D frontend 2.111 with DUB 1.40.0.

Release qualification covers:

- DMD 2.111.0, 2.112.1 and 2.113.0;
- LDC 1.41.0, 1.42.0 and 1.43.0;
- Ubuntu 24.04 x86_64.

## Release process

v0.4 introduces repository-native immutable annotated feature/API freeze
checkpoint automation. Final release tags may be pre-created locally as signed
annotated tags; otherwise the publisher creates an annotated unsigned bot tag.
CI never receives the maintainer's hardware-backed signing key or PIN.

The reviewed v0.4 release-preparation checkpoint is:

```text
67a70e6d6e80a6f515479fc4f1b53bb5f272c61e
```

The final release branch is qualified independently by the full six-compiler
Release Gate before promotion to `main`.

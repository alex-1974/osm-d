# osm-d v0.3.0

v0.3.0 completes the reusable OSM Editing API response boundary without turning
osm-d into an HTTP/account client.

## Highlights

### Parse diff-upload results directly

The new focused facade:

```d
import osm.upload;
```

parses OSM API 0.6 `diffResult` XML into the existing format-neutral
`UploadResult` model.

The reader:

- preserves source order and duplicate placeholder identities;
- preserves raw old/new ID/version fields;
- handles create/modify/delete and conditional-delete response shapes;
- is bounded and transactional through transport-d/dxml;
- deliberately does not infer request action from raw response shape.

Use `UploadResultEntry.effectFor(uploadedEntry, effect)` when semantic
classification is required.

### Discover current server upload limits

The new focused facade:

```d
import osm.capabilities;
```

projects the Editing API capabilities document into the existing
`CapabilityProfile`.

It discovers:

- maximum Way nodes;
- maximum Relation members;
- maximum Changeset elements;
- API version range;
- optional API timeout;
- database/API/GPX service state.

Unrelated map/Notes/GPX query policy, imagery policy and future unrelated
capability subtrees are boundedly skipped under an explicit projection
contract. No openstreetmap.org example limit is compiled in as normative truth.

### Complete store-to-server-response workflow

The reusable semantic chain is now:

```text
PBF/XML
  -> OsmStore
  -> OwnedChangeSequence
  -> validate against discovered CapabilityProfile
  -> osmChange XML
  -> application HTTP/OAuth boundary
  -> diffResult XML
  -> UploadResult
  -> OsmStore.applyUploadResult
```

HTTP requests, OAuth/account state, changeset creation/closing, retry policy,
editor undo/history and application worksets remain outside osm-d.

## API compatibility

v0.3 keeps the supported v0.2 semantic/store/PBF/XML/osmChange/validation
surface and adds `osm.upload` plus `osm.capabilities`.

One deliberately misleading v0.2 compatibility property is removed:

```d
UploadResultEntry.action
```

The property was already documented in v0.2.1 as a context-free shape guess.
Current OSM server behavior makes that guess ambiguous. Migrate to:

```d
UploadResultEffect effect;
if (!entry.effectFor(uploadedEntry, effect))
{
    // result does not acknowledge this request entry
}
```

See `docs/API_V0_3.md` for the complete v0.2 -> v0.3 migration guide and
`docs/API_STABILITY.md` for the frozen v0.3.x contract.

## Toolchain

The compiler floor remains D frontend 2.111 with DUB 1.40.0.

Release qualification covers:

- DMD 2.111.0, 2.112.1 and 2.113.0;
- LDC 1.41.0, 1.42.0 and 1.43.0;
- Ubuntu 24.04 x86_64.

## Performance and baseline scope

M11/M12 add bounded XML response/policy codecs and do not alter the production
PBF decoder, PBF writer or compact-store layout/hot paths. Existing parser and
city-store performance baselines therefore remain the comparison reference.

The v0.3 release gate nevertheless reruns the normal six-compiler package/API
matrix, pinned PBF round-trip, Monaco release-I/O evidence and M6/Bremen store
qualification before promotion.

# osm-d v0.2.0

v0.2.0 is the second qualified standalone osm-d release. It keeps the v0.1
integrity, lifetime and performance contracts while deliberately cleaning the
pre-1.0 consumer surface and completing the editable-store upload bridge.

## Highlights

- one shared semantic leaf vocabulary across PBF and the compact store:
  `LocationView`, `MetadataView`, `TagView`, `NodeRefView` and
  `RelationMemberView`;
- direct typed `OsmStore.node/way/relation(id, ...)` lookup while stable
  `OsmHandle` values remain available for editor identity;
- one-shot `readPbf` and `pbfNodes/pbfWays/pbfRelations` convenience APIs
  alongside the reusable-workspace `PbfReader.read` hot path;
- focused `osm.pbf` and `osm.compare` facades instead of exposing
  specialized PBF facilities from the package root;
- `OsmStore.collectChanges` for deterministic dependency-safe materialization
  of pending store edits;
- format-neutral `UploadResultEntry` / `UploadResult` and
  `OsmStore.applyUploadResult` for authoritative server-ID/version
  reconciliation with stale-response protection.

## Intentional v0.1 -> v0.2 API changes

A Way contains Node references, so the preferred names are now
`NodeRefView` and `OwnedNodeRef`. The v0.1 names `WayNodeView` and
`OwnedWayNode` remain compatibility aliases during the v0.2.x line but are
not package-root exports.

Loss-aware PBF documents/writing and parallel-summary facilities move from the
preferred `import osm;` root to `import osm.pbf;`. Generic semantic
comparison helpers use `import osm.compare;`.

Typed store lookup removes the mandatory `find -> handle -> read` round trip
for ordinary known-ID reads; handle-based access remains supported.

See `docs/API_V0_2.md` for migration examples and
`docs/API_STABILITY.md` for the exact v0.2.x patch-compatibility contract.

## Store -> upload workflow

The store now spans the complete reusable OSM editing semantic cycle:

`PBF/store -> local edits -> OwnedChangeSequence -> osmChange/validation -> diff result -> OsmStore`

`collectChanges` omits clean objects and cancelled local creates, preserves
authoritative baseline version metadata for established deletes, and orders
local dependencies for upload. The caller supplies the changeset explicitly.

`applyUploadResult` takes the exact uploaded semantic snapshot plus the
server result. It validates all result identities and current local state before
acknowledgement, so a delayed response cannot mark newer local work clean.
Create/modify acknowledgements preserve surviving handles; create remaps inbound
references and parent indexes; confirmed delete invalidates the deleted
object's former handle.

Network transport, OAuth/account policy and changeset creation/closing remain
outside osm-d.

## Compatibility

Release floor:

- D frontend 2.111;
- DUB 1.40.0.

Release compiler matrix:

- DMD 2.111.0, 2.112.1, 2.113.0;
- LDC 1.41.0, 1.42.0, 1.43.0.

Release qualification is Ubuntu 24.04 x86_64. Other systems may work but are
not claimed as release-qualified by v0.2.0.

## Evidence

The v0.2 feature tree retains the pinned Geofabrik 2026-09-01 compatibility
corpus and v0.1 parser/reference baseline.

The M9 final store qualification on the v0.2 feature tree passed Monaco and
Liechtenstein direct semantic parity and the Bremen city-scale contract.
Representative Bremen values were:

- direct PBF -> indexed store: 2,284.842 ms;
- final incremental RSS: 347.008 MiB;
- peak/final RSS ratio: 1.070559x;
- logical owned bytes: 308,976,077;
- all semantic/edit/revert/remap checksums matched the straightforward
  reference.

The final release promotion additionally runs the six-compiler Release Gate,
consumer/archive smoke, editor/osmChange interoperability, malformed-input
tests, pinned PBF round trips and release I/O evidence.

See `docs/RELEASE_BASELINE.md` for qualified evidence and interpretation.

## Install

```sdl
dependency "osm-d" version="~>0.2.0"
```

See `docs/GETTING_STARTED.md` and the examples for ordinary PBF traversal,
store editing/upload preparation, PBF rewriting, XML and osmChange.

## Known boundaries

v0.2.0 does not promise ABI stability, a persistent store file format,
concurrent store mutation, rendering/spatial indexing, filesystem/network or
OAuth policy, changeset lifecycle management, or compatibility of low-level
wire/codec/store implementation modules.

Literal JOSM-export provenance remains tracked as evidence hardening in #85;
the release uses independently authored JOSM-/iD-compatible semantic fixtures
and osmium-tool interoperability.
